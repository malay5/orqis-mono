# orqis — deployment

**Two services, not three.** `orqis-backend` currently contains both the
platform API *and* a copy of all 40 agent runtimes, so `orqis-owned-services`
does not need deploying yet. Splitting it out is a P0 follow-up, not a
prerequisite for going live.

```
  Vercel                Render                   MongoDB Atlas
  ┌──────────────┐      ┌──────────────────┐     ┌────────────┐
  │ orqis-       │─────►│ orqis-api        │────►│ orqis      │
  │ frontend     │      │ (orqis-backend)  │     │ (M0 free)  │
  └──────────────┘      └──────────────────┘     └────────────┘
   pages, no DB,         platform API +
   no secrets            40 agents in one
                         process
```

---

## 1. MongoDB Atlas (5 min)

1. Create a free **M0** cluster.
2. Database Access → add a user with *Read and write to any database*.
3. Network Access → allow `0.0.0.0/0`. Render doesn't publish static egress
   IPs on the lower plans, so an allowlist won't work.
4. Copy the connection string and append the database name:
   `mongodb+srv://USER:PASS@cluster.mongodb.net/orqis?retryWrites=true&w=majority`

## 2. Backend → Render

The repo has a blueprint at `orqis-backend/render.yaml`.

**Render → New → Blueprint** → pick the repo → set root directory to
`orqis-backend`.

Secrets to fill in the dashboard (the blueprint marks them `sync: false`):

| Variable | Value |
|---|---|
| `MONGODB_URI` | the Atlas string from step 1 |
| `ENCRYPTION_KEY` | `node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"` |
| `ADMIN_EMAILS` | your email, comma-separated for several |
| `OPENROUTER_API_KEY` | from openrouter.ai/keys — **put a spend limit on it** |
| `CORS_ORIGINS` | your Vercel domain, e.g. `https://orqis.xyz` |

`AUTH_SECRET` is generated by Render automatically. `PUBLIC_BASE_URL` and
`OWNED_SERVICES_BASE_URL` are wired in the blueprint.

**Take the Starter plan ($7/mo), not Free.** The free tier sleeps after 15
minutes idle and the next request takes ~50 seconds. Every page read on the
frontend goes through this service, so a cold start stalls the entire site —
not just agent calls. That will happen during a demo.

### Seed the catalogue

Once the service is up, from Render's Shell tab:

```bash
npm run seed
```

This writes all 40 agents and points each `endpointUrl` at
`OWNED_SERVICES_BASE_URL`. Re-run it any time that variable changes.

## 3. Frontend → Vercel

**Vercel → Add New → Project** → same repo → root directory
`orqis-frontend`. Framework auto-detects as Next.js.

| Variable | Value |
|---|---|
| `ORQIS_API_URL` | your Render URL, e.g. `https://orqis-api.onrender.com` |
| `NEXT_PUBLIC_SITE_URL` | your public domain, e.g. `https://orqis.xyz` |
| `HOME_MODE` | omit — no longer used |

**Set `NEXT_PUBLIC_SITE_URL` before the first deploy.** It drives
`metadataBase`, the sitemap, robots.txt and every canonical and OG URL. Get it
wrong and every canonical tag points at the wrong domain, which is
unpleasant to unwind once indexed.

The frontend holds **no secrets** — no database URI, no signing key. That's a
deliberate property of the split, not an oversight.

## 4. After both are up

```bash
curl https://orqis-api.onrender.com/health          # {"status":"ok","db":{"state":1}}
curl https://orqis-api.onrender.com/v1/catalog/agents | head -c 200
```

Then in a browser: sign up → confirm 5 credits → `/browse` → invoke
`email-truth` → check `/dashboard/credits` shows the debit.

## What is NOT deployed yet, and why

**`orqis-owned-services`** — a byte-identical copy of the 40 agents already
inside `orqis-backend`. Deploying it now would mean running the same code
twice. Split it out when you want independent scaling or when the Playwright
agents need their own memory profile; then point `OWNED_SERVICES_BASE_URL` at
it and re-seed.

**`orqis-py-services`** (bg-strip, subtitle-bot) — Python sidecars. Without
them those two agents stay in mock mode, which is the plan for now.

## Known limits on this setup

- **Browser agents will fail.** page-shot, pdf-render, scrape-render,
  site-crawl, lighthouse-audit and a11y-quick need Chromium (~200 MB per
  call). Render's Starter instance has 512 MB and no Chromium installed.
  They'll fail at invoke time and **auto-refund** the caller, which is correct
  behaviour but not a good demo. Either mock them explicitly or move them to
  a service with a Docker image and more memory.
- **Artifacts are ephemeral.** Files written to `storage/r/` disappear on
  every redeploy — Render has no persistent disk on these plans. Every
  `previewUrl` from a file-emitting agent dies with the next deploy. Cloudflare
  R2 is the fix, in the P0 list.
- **The invocation proxy calls itself.** Because the agents live in the same
  process, an invocation is an HTTP request from the service to its own
  loopback. Node handles this fine (it's async, not blocking), but it does
  mean one external request occupies two connections.
- **`FAKE_PAYMENTS` is on.** Checkout grants credits with no gateway. Do not
  point a real domain at this and call it commerce — see SCALING-TODO.md → P1.
